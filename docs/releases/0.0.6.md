# Release 0.0.6 image promotion

The [reviewed plan](./0.0.6-images.json) promotes the application images accepted
on edge from source revision `1f9d995b7ca30fbad1e85f79c16a25a9bb1f0801`.
Production's image updater selects stable semver tags; it otherwise replaces
manual image digest selections with the older `0.0.5` release.

Run **Promote reviewed release images** on **main**, entering `0.0.6` as
`confirmation_version`. The workflow checks both source digests and both existing
release tags before writing either tag, copies the exact registry manifests with
`--prefer-index=false`, and verifies the published digests. Existing matching tags
are safe to rerun; conflicting tags, authentication failures and transport errors
stop promotion. A partial failure may leave one correctly promoted tag: inspect
the failed run before rerunning. Registry tag writes are not atomic across images
or independent publishers; reserve this version for this workflow, and verify both
live application image identities after the deployment controller reconciles.

The workflow builds no image and changes neither `edge` nor `latest`. It does
**not** create a Git semver tag or a GitHub release. Do not separately push
`v0.0.6`: the existing tag-triggered CI workflow would rebuild and republish these
tags. This is image promotion evidence, not application acceptance or proof that
production data migration and recovery checks passed.

Manifest behavior follows Docker's [create documentation](https://docs.docker.com/reference/cli/docker/buildx/imagetools/create/).
The exact post-copy digest comparison is mandatory even when source format is preserved.
